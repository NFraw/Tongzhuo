# 所有改动建议汇总

从原始设计文档出发，历经三轮讨论，最终收敛的改动清单如下。

---

## 一、架构调整

### 1. 支持自定义服务器地址

**原设计：** 客户端隐式连接固定服务器。

**改动：** 客户端启动后显示连接面板，用户输入任意服务器地址（局域网 IP 或穿透域名）。

```
启动 → 输入服务器地址 → 连接 → 握手 → 进入大厅
```

- `useSocket` 支持动态地址，`connect(url)` 手动触发
- 支持保存历史地址

### 2. 服务器代码抽取为可复用函数

**原设计：** `server/src/index.ts` 是独立入口，与 Electron 无法共用。

**改动：** 抽出 `startServer(options)` 函数：

```typescript
// packages/core/server/index.ts
export async function startServer(options: {
  port?: number      // 用户自定义端口，默认 3000
  host?: string      // 默认 0.0.0.0
}): Promise<ServerHandle>
```

- 独立部署：`server/src/index.ts` 调用 `startServer()`
- Electron 内嵌：主进程直接 import 调用
- `ServerHandle` 返回 `{ port, close() }`

### 3. 穿透职责分离

**原则：** 客户端只负责启动本地服务器并监听用户指定的端口。内网穿透完全由用户自行操作，不集成到客户端中。

**用户流程：**

```
本地开房 → 输入端口（默认 3000）→ 启动服务器
  → 显示局域网地址: http://192.168.1.100:3000
  → 提示: "如需外网访问，请在你的穿透软件中映射端口 3000"
  → 用户自行打开 cpolar/frp/natapp 等
  → 将穿透后的公网域名手动填入客户端
  → 生成外网房间链接
```

客户端不做：
- ❌ 不自动启动穿透进程
- ❌ 不解析穿透软件输出
- ❌ 不管理穿透生命周期

## 二、大厅系统（新增）

### 4. 房间列表协议

**新增事件：**

| 方向 | 事件 | 载荷 | 说明 |
|------|------|------|------|
| S→C | `rooms:list` | `RoomSummary[]` | 连接后推送全量房间列表 |
| S→C | `rooms:update` | `RoomSummary` | 单个房间状态变化 |
| C→S | `rooms:refresh` | - | 客户端主动请求刷新 |

**RoomSummary：**

```typescript
interface RoomSummary {
  roomId: string
  gameId: string
  gameName: string
  players: number
  maxPlayers: number
  phase: 'waiting' | 'playing' | 'ended'
}
```

**广播时机：** 房间创建、玩家加入/离开、满员开始、游戏结束回到等待。

### 5. 连接握手协议

**新增事件：**

| 方向 | 事件 | 载荷 | 说明 |
|------|------|------|------|
| C→S | `player:hello` | `{ playerId, name }` | 连接后立即发送 |
| S→C | `player:welcome` | `{ games: string[], playerId }` | 确认连接，推送游戏列表 |

## 三、稳定性

### 6. 稳定 playerId（替代 socket.id）

**原设计：** `Room.players` 存 socket.id，断线即失效。

**改动：**

```typescript
interface RoomPlayer {
  id: string          // 稳定 UUID，持久化在 localStorage
  name: string        // 昵称
  socketId: string    // 当前活跃连接
  connected: boolean  // 是否在线
  seatIndex?: number
}
```

- 客户端首次启动生成 UUID，持久化存储
- 连接时通过 `player:hello` 上报
- RoomManager 维护 `playerId → socketId` 映射
- 广播时通过 playerId 找到当前 socket

### 7. 断线重连（paused 状态）

**原设计：** 断线直接移除玩家，通知对手，无恢复机制。

**改动：**

```
playing ──断线──> paused ──重连成功──> playing
                    │
                    └──超时(30~60s)──> 对手获胜 / 房间销毁
```

**新增事件：**

| 方向 | 事件 | 载荷 | 说明 |
|------|------|------|------|
| C→S | `player:reconnect` | `{ playerId, roomId }` | 重连请求 |
| S→C | `game:paused` | `{ reason }` | 通知对手游戏暂停 |
| S→C | `game:resumed` | - | 恢复 |
| S→C | `game:forfeited` | `{ winnerId }` | 超时判负 |

---

## 四、游戏生命周期补全

### 8. 游戏结束流程

**原设计：** `checkGameEnd()` 返回赢家后流程不清。

**改动：** 明确 `game:over` 后的行为：

| 方向 | 事件 | 载荷 | 说明 |
|------|------|------|------|
| S→C | `game:over` | `{ winnerId, finalState? }` | 游戏结束，包含赢家和终局信息 |
| C→S | `room:again` | - | 请求再来一局 |
| S→C | `room:againAccepted` | - | 双方同意，房间回到 waiting 并重置 |
| C→S | `room:leave` | - | 离开房间 |

**房间状态机：**

```
waiting ──满员──> playing ──checkGameEnd──> ended
waiting ──玩家离开──> 销毁
playing ──断线──> paused ──超时──> ended
paused ──重连──> playing
ended ──双方同意再来──> waiting（重置状态）
ended ──玩家离开──> 销毁
```

### 9. 客户端状态机补充

**原设计：** `lobby → waiting → playing`

**改动：**

```
lobby ──room:create──> waiting ──stateUpdate──> playing
  │                      │                         │
  │ 加入他人房间          │ 离开                    │ 对手断线
  │                      ▼                         ▼
  │                   (回 lobby)                 paused
  │                                                │
  │                                   重连成功     │ 超时
  │                                     │          ▼
  │                                     ▼        ended
  │                                  playing       │
  │                                     │          │
  │                                     │ game:over│
  │                                     ▼          │
  └──────────────────────────────────> ended <─────┘
```

## 五、接口与安全

### 10. EventResult 接口增强

**原设计：**

```typescript
interface EventResult {
  state: GameState
  broadcast: { event: string; data: any }[]
  error?: string
}
```

**改动：** broadcast 增加目标控制：

```typescript
interface EventResult {
  state: GameState
  broadcast?: Array<{
    event: string
    data: any
    target?: 'all' | 'others' | 'self'  // 默认 all
  }>
  error?: string
  checkEndNow?: boolean  // 是否立即检查游戏结束
}
```

### 11. 房间 ID 强度

**原设计：** `randomBytes(4).toString('hex')` → 8 位 hex（32 bit 熵）。

**改动：**

```typescript
// 方案一：base64url（推荐）
randomBytes(16).toString('base64url')  // 22 字符

// 方案二：至少翻倍 hex
randomBytes(8).toString('hex')  // 16 位 hex（64 bit）
```

### 12. 安全校验清单

`game:action` 处理前必须验证：

- [ ] 玩家属于该房间（playerToRoom 查找）
- [ ] `phase === 'playing'`
- [ ] 事件名合法（插件可校验）
- [ ] payload 结构合法
- [ ] 可选：频率限制（防止刷事件）

`room:join` 处理前必须验证：

- [ ] 房间存在
- [ ] 房间未满
- [ ] 房间未结束
- [ ] 玩家当前不在其他房间

`room:create` 处理前必须验证：

- [ ] gameId 已注册
- [ ] maxPlayers 在合理范围（如 2~10）

## 六、客户端优化

### 13. 动态插件加载

**原设计：** 所有游戏 UI 在 `App.tsx` 静态注册，全部打包进首屏。

**改动：** 按 gameId 懒加载：

```typescript
const clientPlugins = {
  huiming: () => import('games/huiming/ui/client-plugin'),
  doudizhu: () => import('games/doudizhu/ui/client-plugin'),
}

// 加入房间后，根据 room.gameId 动态加载
const plugin = await clientPlugins[room.gameId]()
```

### 14. 状态版本控制

**原设计：** `game:stateUpdate` 直接发送视图对象，网络乱序可能导致旧状态覆盖新状态。

**改动：** 每条更新附带递增版本号：

```typescript
interface StateUpdatePayload {
  state: ClientState
  version: number  // 客户端忽略 version < 当前版本的更新
}
```

## 七、优先级排序

| 优先级 | 改动 | 理由 |
|--------|------|------|
| P0 | 自定义服务器地址 + 连接面板 | 核心需求，没有它无法联机 |
| P0 | 服务器代码抽取 `startServer()` | Electron 内嵌的前提 |
| P0 | 稳定 playerId | 后续所有稳定性的基础 |
| P0 | 大厅协议（rooms:list / update） | 核心需求 |
| P1 | 断线重连（paused） | 真实网络环境必需 |
| P1 | 游戏结束流程补全 | 完整对局体验必需 |
| P1 | 房间 ID 强度 | 一行代码的事 |
| P2 | EventResult 增强 | 插件开发体验 |
| P2 | 动态插件加载 | 游戏多了再做 |
| P2 | 状态版本控制 | 网络差时才有感 |
| P3 | 连接握手协议 | 与 playerId 一起做 |

## 八、修订后的完整协议表

在原始 4.1 节基础上，最终协议总表：

| 方向 | 事件 | 载荷 | 说明 |
|------|------|------|------|
| C→S | `player:hello` | `{ playerId, name }` | 连接握手 |
| S→C | `player:welcome` | `{ games: string[], playerId }` | 握手确认 |
| S→C | `games:list` | `string[]` | 可用游戏列表 |
| S→C | `rooms:list` | `RoomSummary[]` | 大厅房间列表 |
| S→C | `rooms:update` | `RoomSummary` | 房间状态变化 |
| C→S | `rooms:refresh` | - | 主动刷新 |
| C→S | `room:create` | `{ gameId, maxPlayers? }` | 创建房间 |
| S→C | `room:created` | `{ roomId }` | 创建成功 |
| C→S | `room:join` | `{ roomId }` | 加入房间 |
| S→C | `room:joined` | `{ players: RoomPlayer[] }` | 加入成功，返回完整玩家列表 |
| S→C | `room:error` | `{ reason }` | 房间错误 |
| C→S | `room:leave` | - | 离开房间 |
| C→S | `room:again` | - | 请求再来一局 |
| S→C | `room:againAccepted` | - | 双方同意 |
| C→S | `player:reconnect` | `{ playerId, roomId }` | 断线重连 |
| C→S | `game:action` | `{ event, payload }` | 游戏操作 |
| S→C | `game:stateUpdate` | `{ state, version }` | 状态更新（独立视图） |
| S→C | `game:error` | `{ reason }` | 操作错误 |
| S→C | `game:over` | `{ winnerId, finalState? }` | 游戏结束 |
| S→C | `game:paused` | `{ reason }` | 对手断线暂停 |
| S→C | `game:resumed` | - | 对手重连恢复 |
| S→C | `game:forfeited` | `{ winnerId }` | 对手超时判负 |

---

这就是从原始设计到现在的全部改动汇总。核心方向：**从「单一服务器 + 浏览器」架构，升级为「Electron 桌面端 + 可内嵌服务器 + 用户自选连接地址」的去中心化架构，同时补全大厅、重连、游戏生命周期等真实场景必需的能力。**
